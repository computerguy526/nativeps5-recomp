# x87 full 80-bit mode (`-x87 f80`, the default)

Branch m2-x87f80. Decision and measurements: `work/x87/X87-DECISION.md`. Today's double model stays as `-x87 f64`
(unchanged, bit for bit).

## What it is

* `ps4-recomp -x87 f80|f64` (default `f80`; `pkg/cli`, `Arm64Lifter.SetX87Mode`). The mode is per translation (per title);
  the log prints it. Per-function overrides (`x87_f64_funcs`) are not implemented: the two models keep their registers
  in different places (below), so mixing them at a function boundary would need a conversion.
* Lowering (`pkg/lifter/arm64_lifter_x87f80.go`): every x87 instruction is `movz w0,#op; [x1 = host pointer]; bl _recomp_x87`.
  The bridge (`pkg/emitter/asm_x87.go`, appended to the trampoline) saves NZCV, x8-x15 and v0-v7, calls
  `recomp_x87_impl(ctx, op, arg)` and restores everything but x0 (result: status/control word, or NZCV bits for FCOMI).
  See Performance for what is and is not saved, the inline paths and the batch entry `_recomp_x87_run`.
* Runtime (`pkg/runtime/core/nps5_x87.c`, `nps5_x87.h`): arithmetic on Berkeley SoftFloat 3e, 8086-SSE specialization
  (`pkg/runtime/core/softfloat`, BSD-3-Clause, listed in NOTICE; x87 default NaN, NaN propagation, integer indefinite).
  RC and PC are read from the control word per call (`softfloat_roundingMode`, `extF80_roundingPrecision`; both
  thread-local). The op word layout is in `nps5_x87.h` and mirrored in the lifter (`TestX87KindsMatchHeader`).
* GuestContext: existing offsets untouched. Appended: `x87_reg_t fpu80[8]` (0xbd0; 16-byte slots, significand + sign/exponent,
  physical register order) and `fpu_valid` (0xc50; bit n = register n not empty). TOP, CW and SW stay in `fpu_top`,
  `fpu_cw`, `fpu_sw` (0x2e0/0x2e4/0x2e6; SW is kept without TOP, which is merged when read). `recomp_context.h` asserts both
  new offsets. The f64 model keeps using `fpu_stack`.

## Instructions (f80)

FLD/FST/FSTP m32/m64/m80/st(i); FILD/FIST/FISTP/FISTTP 16/32/64; FLD1/FLDZ/FLDL2T/FLDL2E/FLDPI/FLDLG2/FLDLN2 (exact 64-bit
values, rounded by RC like the hardware); FADD/FSUB/FSUBR/FMUL/FDIV/FDIVR and the P forms, ST(i) and m32/m64 forms;
FIADD/FISUB/FISUBR/FIMUL/FIDIV/FIDIVR m16/m32; FCHS/FABS/FSQRT/FRNDINT/FSCALE/FXTRACT/FPREM/FPREM1 (FPREM is exact, with
C0/C3/C1 = Q2/Q1/Q0, and returns a partial remainder with C2 = 1 when the exponent difference is >= 64);
FCOM/FCOMP/FCOMPP/FUCOM/FUCOMP/FUCOMPP/FICOM/FICOMP/FTST/FXAM, FCOMI/FCOMIP/FUCOMI/FUCOMIP; FXCH; FLDCW/FNSTCW/FNSTSW (AX and
m16)/FNINIT/FNCLEX/FWAIT; FCMOVcc; FFREE/FFREEP; FDECSTP/FINCSTP; FNSTENV/FLDENV/FNSAVE/FRSTOR (28-byte and 16-bit operand
size formats); FXSAVE/FXRSTOR (the x87 half through the helper; the XMM half is the existing lowering); FBLD/FBSTP.
PC = 24/53/64 bits and RC are honoured by the arithmetic and by the stores to m32/m64; FIST rounds by RC.

Status word: IE, ZE, OE, UE, PE from SoftFloat's flags (sticky), SF + IE + C1 on stack overflow/underflow with the
indefinite as the masked response, C0-C3 for compares, FPREM and FXAM. The tag word is derived from `fpu_valid` and the
register contents (valid/zero/special/empty) when FNSTENV/FNSAVE store it, and `fpu_valid` is restored from it.

## Not done

* FSIN, FCOS, FSINCOS, FPTAN, FPATAN, F2XM1, FYL2X, FYL2XP1: translate-time unsupported in f80 mode (as in f64). None of the
  scanned binaries uses them, and matching the hardware's results (66-bit pi reduction, polynomial) would need more than a
  host libm. They are ~27 of the 217 FEX X87 tests (skipped).
* Undocumented encodings FCOM2/FCOMP3/FXCH4/FCOMP5/FXCH7/FSTP8/FSTP9 (DC D0, DC D8, DD C8, DE D0, DF C8, DF D0, DF D8):
  `golang.org/x/arch/x86/x86asm` does not decode them (7 FEX tests fail with brk 0x779).
* Unmasked exceptions are never delivered (only the flags are set); DE (denormal operand) is not set; C1 is not set for
  "rounded up"; FIP/FDP are stored as 0.
* MMX aliasing is partial: in f80 mode MMX register n reads and writes the significand of `fpu80[n]` (the lifter rewrites
  the offsets), but an MMX write does not set the exponent to 0xFFFF, TOP to 0 or the tags (FEX `X87MMXInteraction`).
* x87=f64 and f80 do not interoperate within one process (separate register storage).
* FDIV/FSQRT, FIST/FISTP (RC), FST/FSTP m32/m64 and the rounded constants are still SoftFloat helper calls;
  FADD/FSUB/FSUBR/FMUL and the compares run on an exact integer fast path (m3-x87fast, below) and use SoftFloat
  only for denormal/Inf/NaN operands or a result outside the normal range; the data movement is inline.

## Performance (branch m3-x87perf)

* **Bridge.** Saves NZCV, x8-x15 (to ctx, reloaded) and v0-v7 only. x19-x28 and v8-v15 low halves are callee-saved by the C
  code; v8-v31 are never touched by `nps5_x87.c` and the SoftFloat subset (`TestX87RuntimeVectorRegs` disassembles the objects
  at -O1/-O2/-O3/-Os with `-mcpu=apple-m1` and fails on any use of v8-v31, so a compiler change cannot silently break the
  contract). The guest GPRs x19-x26 are no longer stored to ctx (nothing in the helpers reads them).
  `TestX87OptMatchesReference` loads v0-v31 with a pattern and NZCV with a known value before every program and checks
  them after, with the very first program calling the helper first (thread-local state created with all registers live).
* **Inline** (`pkg/lifter/arm64_lifter_x87inline.go`, x16 = ctx, scratch x0-x7/x17, no vector register, no flag-setting
  instruction: `TestX87InlineKeepsFlags`): FLD st(i), FST/FSTP st(i), FXCH, FCHS, FABS, FLD1, FLDZ, FLD m80, FSTP/FST m80,
  FLD m32/m64 (normal numbers; zero, denormal, Inf, NaN take the helper), FILD m16/m32/m64 (exact, clz), FISTTP m16/m32/m64
  (|x| < 2^n or < 1, PE set when bits are cut off), FFREE/FFREEP, FINCSTP, FDECSTP, and FNSTSW/FNSTCW/FLDCW as moves of
  ctx fields. Every inline sequence that can meet a stack overflow, underflow, an out-of-range or special value changes
  nothing before it branches to the ordinary bridge call with the same op word, so all exceptional behaviour stays in the C
  helper. Not inline: arithmetic, compares, FIST/FISTP (RC), FST/FSTP m32/m64, FLDPI & co (rounded by RC), FSQRT...
* **Batching.** `Arm64Lifter.SetBlock` (called by the emitter and fexasm per basic block) lets the lowering look ahead: a run
  of 2 to 16 consecutive helper operations (inline-able ones between them ride along; a trailing FCOMI/FUCOMI(P) is allowed,
  its NZCV comes back in x0) becomes `sub sp; (op word, pointer) pairs; bl _recomp_x87_run; add sp`. The C side
  (`recomp_x87_run_impl`) sets SoftFloat's rounding mode and precision once per batch (each thread-local access is a call on
  this platform). The PC map attributes the whole batch to its first instruction. Without `SetBlock` (unit tests) nothing is batched.
* `Arm64Lifter.SetX87Opt(inline, batch)` turns both off: that is the reference lowering of `TestX87OptMatchesReference`,
  which compares inline, batch and both against it over 600 random sequences (stack overflow/underflow, FFREE, control word
  changes, NaN/denormal/Inf operands, FCOMI/FCMOV flag results) plus directed ones: TOP, SW, CW, tags, all eight registers,
  RAX, memory, NZCV and v0-v31 must be bit-identical. `TestX87FastConversions` checks the C fast conversions (f32/f64
  normal -> f80, integer -> f80) against SoftFloat over 20M random inputs.

Benchmark (`x87_bench.c`, now also with a printf-like `%f` loop; built with `-DCPUTIME` it reports thread CPU time):

| thread CPU ns, min of 3 interleaved runs, load avg ~35 (before/after under the same load) | before | after | speedup |
|---|---:|---:|---:|
| `acc = acc*c + d`, per iteration | 50.5 | 31.9 | 1.6x |
| digit extraction, per digit | 53.1 | 27.4 | 1.9x |
| printf-like `%f` loop, per value | 257 | 105 | 2.4x |

The 3x target is not reached on the arithmetic-bound loops: what is left is SoftFloat itself. In a native micro-benchmark
(thread CPU time) `extF80_mul` costs 6.4 ns and `extF80_add` 6.7 ns, of which about 1.5 ns each are the thread-local
state accesses (a call per access on Apple arm64; a non-thread-local build is 5.4/4.3 ns), and the helper dispatch around them
about 6 ns per operation. The chain loop is two such operations per iteration. Next steps if a title needs it: exact
fast paths for normal-operand ADD/SUB/MUL under PC = 64 and RC = nearest (differentially tested against SoftFloat), inline
compares, and a per-thread SoftFloat state without thread-local calls. `-x87 f64` remains the escape hatch.

## Default control word and the fast paths (branch m3-x87fast)

**The PS4/PS5 default x87 control word is 0x037F (64-bit precision, round to nearest, all exceptions masked), not
0x127F.** 0x127F is FreeBSD/*i386*'s `__INITIAL_NPXCW__` (53-bit precision); amd64 uses `__INITIAL_FPUCW__ = 0x037F`
("For FreeBSD/amd64, we go with the default settings"; `x86/fpu.h` in both the testbed SDK and the payload SDK's
`target/include`). Evidence:

* SDK: `testbed/sdk/include/freebsd/x86/fpu.h` and `ps5-payload-sdk/.../target/include/x86/fpu.h` (lines 188-206): FPUCW 0x037F,
  NPXCW (i386 only) 0x127F, MXCSR 0x1F80. The SDK's libc/crt (`libc/_setjmp.S`, `crt/`) only save/restore the word
  (`fnstcw 64(%rax)` / `fldcw 64(%rdx)`); nothing calls FNINIT or FLDCW with a constant.
* AnyPS5 (read-only): `core/libs/tests/GuestKernelSysThreadDefaults.cpp` (`CheckFpuControl`) requires a new
  `scePthread` thread to start with `fnstcw == 0x037f` whatever the creator set (it sets 0x027f first). Its libc
  (`FloatingPoint.cpp`, `Math.cpp`, `JumpBuffer.cpp`) only reads/modifies the word (fesetround/fesetexcept, `| 0x3f`, longjmp restore).
* The user's title (PPSA30552 eboot.bin and sce_module/libc.prx, linear-sweep decode of the executable segments, nothing
  copied): eboot.bin has **0** FLDCW/FNSTCW/FNINIT/FLDENV/FNSTENV (36 x87-looking decodes in the whole 141 MB image, probably
  desynchronised data); libc.prx has 7 FLDCW (0x11e9a, 0x11ed8, 0x12045, 0x120a2, 0x1218d: fenv/fesetround-style
  read-modify-write of the word from `fnstcw`, bits 0x3f/0xc00; 0x543b7 and 0x114541: `fldcw 0x40(%rdx)` in longjmp), 6 FLDENV
  (fesetenv family), 9 FNSTCW, 8 FNSTENV, 1 FXRSTOR, **0 FNINIT and no constant control word anywhere**; 4789 x87 instructions
  (libm / long double printf). So titles run at PC = 64, RC = nearest unless they call fesetround.
* Our runtime: `recomp_runtime.c` initialises `fpu_cw = 0x037F` for the main context (line 557, again at 612) and copies the
  parent's word for new threads; the fiber code and the FEX/difftest harnesses use 0x037F; `fninit` in `nps5_x87.c` also
  sets 0x037F (the real FNINIT value). Nothing to change; the old assumption "PC = 53 is the console default" is wrong, so the
  planned PC = 53 hardware-double fast path would not have been used by default.

Consequence for the design: the default is the *hard* case (64-bit significands do not fit a host double), so the fast path is
integer arithmetic on the 64-bit significands, exact for PC = 24, 53 and 64 and every RC, instead of a hardware f64/f32
operation. The PC = 53 double route (convert, `fadd d`, check) would only help the rare PC = 53 title and is subsumed.

### Exact integer fast path (`fast_addsub`, `fast_mul`, `fast_cmp` in `nps5_x87.c`)

FADD/FSUB/FSUBR/FMUL (ST(i) and m32/m64/m16int/m32int forms, P variants) and FCOM/FCOMP/FCOMPP/FUCOM*/FCOMI*/FTST/FICOM on
operands that are zero or normal (exponent field 1..0x7ffe, integer bit set): add/sub aligns the smaller operand in a 128-bit
integer with sticky jamming, normalises with clz, multiplication is one `mul`/`umulh`; the result is rounded to the PC
significand with RC (nearest-even, down, up, toward zero) and PE is raised iff the result is inexact. Declined (SoftFloat as
before, nothing changed): denormal/unnormal operands, Inf, NaN, an empty source register (stack underflow), a result whose exponent
leaves 1..0x7ffe (overflow, underflow, tiny), two zero operands, FDIV, FSQRT. An exact zero result from x - x is
handled inline (+0, or -0 for RC down); a zero operand with a normal one is handled (result rounded to PC). No SoftFloat state (thread-local rounding mode/precision/flags) is touched, so the SoftFloat
environment is set lazily, only when an operation really needs it.

`TestX87FastArith` (`go test -run TestX87FastArith`; `-short` = 50 k pairs) compiles `nps5_x87.c` with SoftFloat and compares, for ADD/SUB/SUBR/MUL x PC {24,53,64} x RC {0..3},
1.5 million operand pairs each (72 M results; 80% take the fast path) including ties, all-ones significands, double/float-exact
significands, exponent differences 0..80, exponents at both range limits, zeros, denormals, Inf, NaN, unnormals, x-x and
x+(-x): value and inexact flag must be identical (0 differences); 6 M compare pairs against `compare()`. Mutations of the
tie rule or the sticky handling are caught. `TestX87OptMatchesReference` now takes its reference from a runtime built with
`-DNPS5_X87_NOFAST` (everything on SoftFloat, no lean entries), so the 600+ sequence comparison (inline, batch, both) is
fast path + lean bridge against pure SoftFloat, bit-identical incl. TOP/SW/CW/tags/registers/NZCV/v0-v31. The FEX X87 (185) / X87_F64 (112) PASS counts are unchanged.

### Lean bridge entries (`preserve_most`)

`recomp_x87_fast` / `recomp_x87_run_fast` (`__attribute__((preserve_most, flatten))`, integer only) are called first by the new
bridge entry `_recomp_x87_a` (single arithmetic/compare instructions) and by `_recomp_x87_run`. The bridge saves NZCV and x8
only (the compiler saves the x9-x15/x19/x20 it uses; v0-v7 are not touched, `TestX87RuntimeVectorRegs` fails on any vector
register or call in those two functions at -O1/-O2/-O3/-Os); when the fast entry declines (done = 0) the old full path runs with
the remaining operations. Apple clang 21 and Homebrew LLVM both support `preserve_most`/`preserve_all`; `preserve_all` was not
needed. Batches are now only built when they replace at least two full bridge calls (>= 2 operations the fast entry never
runs, e.g. FDIV, FST m32/m64): a run of fast operations is cheaper as separate `_recomp_x87_a` calls.

### Numbers (x87_bench.c, `tools/x87_bench.sh [-pc53]`, thread CPU ns, interleaved min of 6 against a main build)

Load average 20-27 on a shared machine for both columns of a row (`uptime` printed by the script; absolute numbers are inflated
by SMT contention, the ratio is what counts). `acc*c+d` = fmul+fadd per iteration, digit = fmul/fisttp/fild/fsub, printf = `%f`-like value.

| | main 7b5453b | + integer fast path only (separate run, load ~14: 32.4/31.2/110 -> 24.2/23.5/78) | final (+ lean entries, batching rule) | speedup |
|---|---:|---:|---:|---:|
| PC=64 `acc*c+d` | 31.6 | 0.75x | 16.2 | 1.95x |
| PC=64 digit | 28.6 | 0.75x | 16.7 | 1.7x |
| PC=64 printf-like | 103.7 | 0.71x | 57.3 | 1.8x |
| PC=53 `acc*c+d` | 26.0 | | 15.4 | 1.7x |
| PC=53 digit | 28.4 | | 17.2 | 1.65x |
| PC=53 printf-like | 100.4 | | 58.9 | 1.7x |

Results are identical (`1107014.951133`, same digit sums). That is about 8 ns per arithmetic instruction instead of ~16

round trip of every x87 register.

### Not done, and why

* **Inline lowering of the arithmetic.** An inline add needs ~100 instructions (operand fetch with TOP/tag checks, ordering,
  128-bit alignment shift with jamming, normalisation, rounding, range check, commit); the lean call path is ~60. The chain loop
  is also latency-bound: every x87 instruction stores its result to `fpu80[]` and the next one loads it back (4 dependent
  memory round trips per iteration), so the lever is the next item, not instruction count.
* **FEX-style stack optimisation (X87StackOptimizationPass).** Not implemented. FEX's pass is not in the sparse clone
  (`repos/FEX/FEXCore` has only `Source`/`Interface` without it), so this is a design sketch only: per basic block track a
  static TOP offset relative to the entry TOP, check stack fullness/emptiness once at block entry for the whole block (the
  underflow/overflow outcome is then known, so the per-operation tag checks go away), keep each logical ST(i) in an arm64
  register (a 64-bit significand + 16-bit sign/exponent pair: x-registers, or one q register), and write the registers back to
  `fpu80[]`, `fpu_top`, `fpu_valid` at the block exit and before anything that can leave the model (SoftFloat helper
  calls, FLDCW/FNSTENV/FXSAVE, memory forms that fault, calls). It needs a rework of the lowering from per-instruction
  to per-block with register assignment and is the right next step for latency-bound loops.
* PC = 53 / PC = 24 hardware double/float route, see above.
* FDIV (exact 128/64-bit quotient needs a division the host lacks), FSQRT, FIST(P) under RC, FST m32/m64.
