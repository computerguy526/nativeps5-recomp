# S1 report: address space, faults, ordering on native arm64 (Apple M4 Pro, 24 GB, macOS 26.6.2, clang 21)

All code in this directory; `./build.sh` builds everything (native arm64, `-O2`). Raw outputs: `membench.out`, `litmus.out` (5M iters), `litmus40.out` (40M iters).

## 1. Address space (§3.6)

**Method.** `vmmap -v` on a trivial native process; `mach_vm_allocate(VM_FLAGS_FIXED)` (no OVERWRITE, so it fails instead of clobbering) for the 560 GiB `0x70_0000_0000`-`0xFC_0000_0000` reservation after a `mach_vm_region` free-check, then `mach_vm_protect(NONE)`, then `mprotect(RW)` + touch of 4 MiB sub-regions at fixed offsets (+0, +1 GiB, +0x10_0000_0000, +0x30_0000_0000 ...) and the last 16 KiB page. `addr.m`; 10 launches each of: no Metal, Metal device created before the reservation, Metal device created after.

| Result | Value |
|---|---|
| Carveout (vmmap -v, 4 launches incl. Metal) | `0x10_0000_0000`-`0x70_0000_0000` (384 GiB) "GPU Carveout (reserved)", **identical to the M1 Pro numbers in limits.md** |
| 560 GiB fixed `mach_vm_allocate` at `0x70_0000_0000` | success 30/30 launches (none / Metal-before / Metal-after); `mach_vm_region` free-check passed every time |
| mprotect(RW)+touch of sub-regions, last page `0xFB_FFFF_C000` | all OK, also after Metal init; reservation survived Metal init (Metal creates its own small mappings, none collide) |
| vmmap with reservation | `VM_ALLOCATE 7000400000-...-fbffffc000 ---/rwx`; mprotect splits entries (fine) |
| Zero-fill Mach-O segment `-segaddr __RSV 0x7000000000`, 560 GiB, `-segprot rw,rw` | loads and works (RSS ~1 MB), **but lands at 0x70_0000_0000 + ASLR image slide** (observed slides 0x4_0000..0x4F1_4000, up to ~80 MB; `-no_pie` is ignored on arm64). Not an exact fixed base. Also `adrp` cannot reach a >4 GiB-away symbol: address it as a constant plus `_dyld_get_image_vmaddr_slide`. |

**Surprises (affect §3.6 text).**
1. 0x2_0000_0000-0xF_C000_0000 is **not** a clean second arena. `vmmap -v` shows: dyld shared cache/commpage `0x1_8000_0000`-`0x3_0000_0000` (commpage reserved at `0x1_8000_0000`, 51 MB, not near `0xF_C000_0000` as §3.6 says); two **per-launch randomised 12 GiB "GPU Carveout" windows** (e.g. `0x5_B600_0000-0x8_B700_0000` and `0x8_B740_0000-0xB_B600_0000`, start moving 0x5_54..0x7_DA across launches; both sit in 0x5_5400_0000-0xDD_A000_0000); and a fixed 1 GiB carveout `0xF_C000_0000`-`0x10_0000_0000`. Fixed-2 MiB probe in one launch: free `0x3_0000_0000`-`0x7_D000_0000`, taken `...`-`0xD_D000_0000`, free `0xD_D000_0000`-`0xF_C000_0000`. Launch-invariant free space below the carveout is only ~`0x3_0000_0000`-`0x5_5400_0000` (~21 GiB) and `0xD_DA00_0000`-`0xF_C000_0000` (~8.5 GiB). R-ADDR window is larger than 384 GiB: effectively 0x1_8000_0000-0x70_0000_0000 minus a few small free pockets.
2. Probe of `0x2_0000_0000` fails here (shared cache); limits.md saw it map on M1. Do not depend on it.
3. `0x70_0000_0000` through `0x101_0000_0000` probed free (2 MiB fixed probes), so the arena's upper bound `0xFC_0000_0000` is not constrained.

## 2. Fault cost (§3.6 / R5) - `fault.c`

16 KiB page: `mprotect(R)`, write, SIGSEGV/SIGBUS handler `mprotect(RW)` and return. Timed write-to-resume (includes kernel trap, signal frame, handler's mprotect, sigreturn); each thread uses its own pages; 20k faults/thread; mach_absolute_time (41.7 ns tick, so p50 is good to ~±40 ns).

| threads | median ns | p90 | p99 | p99.9 | faults/s aggregate | mprotect(R) call |
|---|---|---|---|---|---|---|
| 1 | 3125 | 3542 | 5167 | 8917 | 251k | 715 ns |
| 2 | 4084 | 5583 | 8500 | 16166 | 374k | 863 ns |
| 4 | 6084 | 16542 | 60834 | 149417 | 376k | 970 ns |
| 8 | 24083-29083 | ~110k | 247-280k | 0.4-0.9 ms | 155-161k | 1.6-2.0 us |

Single-thread ~3.1 us per write-watch fault; scales poorly: aggregate throughput plateaus at ~375k/s at 2-4 threads and collapses at 8 (mprotect takes the task VM map lock, p99 up to 0.28 ms). Mach exception port path not measured (optional); it is usually slower than a signal for an in-process handler.

## 3. Memory ordering (§3.5) - `membench.c`, `litmus.c`

CPU: `hw.optional.arm.FEAT_LRCPC=1`, `FEAT_LRCPC2=1`. LDAPR/STLR used; for offset addressing LDAPR has no offset form (LDAPUR/STLUR exist with LRCPC2). Plain figures best-of-5.

| Test | plain | LDAPR / STLR | LDAR | dmb ish bracketed | LDAPR vs plain |
|---|---|---|---|---|---|
| pointer-chase L1 (16 KiB), ns/load | 0.78 | 0.76 | 0.76 | 0.76 | ~1.0x (noise +-5%) |
| pointer-chase L2 (1 MiB) | 7.38 | 7.97 | 7.35 | 7.22 | 1.0-1.08x |
| pointer-chase DRAM (64 MiB) | 112 | 118 | 116 | 115 | 1.0-1.05x |
| streaming load-sum L1 | 0.119 | 0.287 | 0.276 | 0.407 (ldr+dmb ish) | 2.4x |
| streaming load-sum 64 MiB | 0.145 | 0.302 | 0.303 | 0.497 | 2.1x |
| streaming store L1 | 0.146 | 0.264 (STLR) | - | 4.52 (dmb+str+dmb) | 1.8x (dmb: 31x) |
| streaming store 64 MiB | 0.144 | 0.357 (STLR) | - | 12.6 (dmb+str+dmb) | 2.5x (dmb: 87x) |

Latency-bound code sees no cost; throughput-bound loops lose the load/store pipelining width (ldr ~8/cycle-class throughput vs ~2x worse for acquire/release), 2-2.6x worst case, and a full `dmb ish` around every access is 3.4x on loads and 30-87x on stores.

**Litmus** (2 threads, per-iteration barrier-aligned, results `r0,r1`). SB: `(0,0)` is *allowed* by x86-TSO (only MFENCE forbids it), so it is reported, not a failure. MP: `r0=1,r1=0` (flag seen, data stale) is the TSO-forbidden outcome.

| Mapping | SB (0,0) /5M | SB (0,0) /40M | MP forbidden /5M | MP forbidden /40M |
|---|---|---|---|---|
| plain LDR/STR | 26 | 4692 | 0 | **2** |
| STLR + LDAPR | 64 | 942 | 0 | 0 |
| STLR + LDAR | 0 | 0 | 0 | 0 |
| dmb ish between | 0 | 0 | 0 | 0 |

Plain accesses violate MP (2 in 40M, rare on Apple cores but real: Apple's silicon is not TSO unless the TSO bit is set); STLR/LDAPR and DMB did not. LDAPR still allows SB (0,0), which TSO allows too, so it is not a violation; LDAR/DMB forbid it (stronger than x86 needs). Hardware tests cannot prove correctness (0 in 40M is not a proof); §3.5's requirement for a model-based check stands.

## 4. TSO enable (§3.5)

Public sysctls tried (all `unknown oid`/ENOENT, write attempt ENOENT): `hw.optional.tso`, `hw.optional.arm.FEAT_TSO`, `hw.optional.arm.FEAT_TSO_EL0`, `machdep.tso`, `machdep.cpu.tso`, `kern.tso`, `hw.tso`, `kern.proc_translated`. `sysctl.proc_translated` exists (=0 natively; read-only status). `sysctl -a` has no tso/rosetta/oah knob. SDK headers: no TSO API. `dlsym` for guessed names (`thread_set_tso`, `pthread_set_tso_np`, `proc_set_tso`, `thread_enable_tso`): absent. `strings`/`codesign -d --entitlements` on `/Library/Apple/usr/libexec/oah/{runtime,libRosettaRuntime,oahd}` show no TSO string or entitlement; Rosetta's mechanism is a kernel-set per-process/thread state applied to x86-64 translated processes, with no user-space call. (Not tested: Virtualization.framework Rosetta-for-Linux, which enables TSO only for guest Linux threads and requires `com.apple.security.virtualization`; no private entitlement or kernel route was pursued.) **Result: no supported way to enable hardware TSO for a third-party native arm64 process.**

## Conclusions

**§3.6 arena: viable.** A single 560 GiB `0x70_0000_0000`-`0xFC_0000_0000` `PROT_NONE`/no-access reservation via collision-checked `mach_vm_allocate(VM_FLAGS_FIXED)` succeeds first try on M4 Pro (30/30 launches, Metal before or after), sub-regions can be mprotect'ed and touched at fixed offsets. Use that, not the `-segaddr` segment (image slide makes the base non-exact; it is only usable if the base is read at runtime and a ~256 MiB margin is left). Usable range for guest identity mapping: `0x70_0000_0000`-`0xFC_0000_0000`, carveout `0x10_0000_0000`-`0x70_0000_0000` confirmed. Correct §3.6: the low region is not a second arena (random 12 GiB reserved windows + shared cache); only ~21 GiB `0x3_0000_0000`-`0x5_5400_0000` is launch-stable. R-ADDR stands: a fixed 0x30_0000_0000 request cannot be served. Vulkan/KosmicKrisp-in-process was not tested (only Metal); repeat in S3.

**§3.5 default: LDAPR/STLR mapping is the best candidate** (1.0x on latency-bound, ~2-2.6x worst case on streaming; passed all litmus runs) but, per spec, stays a candidate until model-validated; full-barrier baseline costs 3.4x (loads) and 30-87x (stores) on tight loops, too slow for release. Treat hardware TSO as unavailable; plain accesses are observably unsafe (MP violation seen). Keep RSP/RBP-relative accesses plain only where thread-private, and use LDAPUR/STLUR to avoid an add for displacement addressing.

**R5 fault cost:** ~3.1 us/fault single-thread, ~25 us median and 0.3 ms p99 at 8 contending threads; write-watch must be coarse (batch/ranges, avoid per-page re-arming in hot paths).
